# Auth Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete sign-up (with required email confirmation), sign-in, sign-out, protected routes, expired-session recovery, password reset, and automatic profile provisioning.

**Architecture:** `@supabase/ssr` keeps the Supabase session in cookies; `client/proxy.ts` refreshes it on every request and redirects using a pure `decideRedirect` function. Email links hit a `/auth/confirm` route handler that calls `verifyOtp` with a `token_hash`. The client provisions the profile through the existing `PUT /api/v1/userprofiles/me`.

**Tech Stack:** Next.js 16 (App Router, `proxy.ts`), React 19, `@supabase/supabase-js` 2.112.3, `@supabase/ssr`, Vitest, Playwright, Supabase CLI (local test stack only), ASP.NET Core / xUnit v3.

**Spec:** `docs/superpowers/specs/2026-10-21-auth-flow-design.md`

## Global Constraints

- Supabase (hosted) stays for Auth + DB; the local Supabase CLI stack is a test harness only.
- No premium tier, paywall, or billing anywhere.
- Email confirmation is required; no session before confirmation.
- Minimum password length: `8` (client constant `MIN_PASSWORD_LENGTH = 8`; Supabase `minimum_password_length = 8`).
- Resend cooldown: `60` seconds.
- Every page under `client/app/(app)` (including `/`) requires a session.
- Raw Supabase error messages are never rendered; only `toAuthMessage` output.
- `UpdateUserProfileRequest` limits: `FullName` ≤ 100 chars, `UserType` ≤ 50 chars, both required.
- No new API endpoints.
- Copy (verbatim):
  - Expired: "Your session expired. Please sign in again."
  - Reset sent: "If an account exists for that email, we've sent a reset link."
  - Error map: see Task 3.

**Deviations from the spec's module table (decided here):**
- `ensureProfile` lives in `client/lib/profile.ts`, not `lib/auth.ts`, because `lib/api.ts` already imports `lib/auth.ts` and the reverse import would be circular.
- `safeRedirect`/`decideRedirect` live in `client/lib/auth/redirects.ts`; `toAuthMessage` and validation live in `client/lib/auth/messages.ts` and `client/lib/auth/validation.ts`. `client/lib/auth.ts` stays where it is and re-exports nothing new from them.
- The API's `RequireHttpsMetadata` becomes `false` only when `Supabase:Url` is a loopback `http` URL, so the local e2e stack works (Task 9). Production behavior is unchanged.

## Review Focus

1. **Sign-up name longer than 100 chars (or user type longer than 50)** → `PUT /me` would 400 and the profile would never exist. Expected: `ensureProfile` truncates to the limits; empty/missing values fall back. Test in Task 5.
2. **Initial session restore and `SIGNED_IN` firing together** → two concurrent `ensureProfile` calls racing two inserts on the same primary key. Expected: one in-flight call per user id. Test in Task 5.
3. **`next` pointing into `/auth/*`** (e.g. `/auth?next=/auth/check-email`) → loop or landing on an auth page after login. Expected: `safeRedirect` returns `/` for any path under `/auth`. Test in Task 1.
4. **Email typed with spaces or capitals** (`" Jane@Example.com "`) → "invalid email" or a duplicate account. Expected: trimmed and lower-cased before every Supabase call. Test in Task 3.
5. **Deep link with a query string** (`/applications?status=draft`) → query lost after login. Expected: `next` carries pathname + search. Test in Task 1.
